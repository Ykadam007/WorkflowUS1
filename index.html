Payment verification

Why the backend trusts the webhook, not the browser

The browser confirms "payment succeeded" instantly, but that message can be spoofed, dropped, or replayed. StayFlow's backend only confirms a booking after the payment gateway independently calls back and the signature checks out.

Python / Django — the fix

with transaction.atomic(): room = RoomInventory.objects.select_for_update().get( hotel_id=hotel_id, room_type=room_type ) # row is now locked until this block commits or rolls back if room.available_rooms <= 0: raise RoomUnavailable() room.available_rooms -= 1 room.held_rooms += 1 room.save()

transaction.atomic() — the booking operations succeed together or roll back together. select_for_update() — locks the matching inventory row so no other request can read or modify it until this transaction finishes.

KEY TAKEAWAY

A booking system is not just Search → Pay → Confirm

A reliable implementation has to account for change and contention at every step:

  • Availability changing between search and reserve
  • Concurrent bookings for the same room
  • Database transactions & row locking
  • Temporary holds with expiry
  • Payment verification via webhook
  • Idempotency for duplicate requests
  • Rollbacks that restore inventory
  • Confirmation & notification delivery
Inventory must stay correct even when thousands of people try to book the same room at once.
